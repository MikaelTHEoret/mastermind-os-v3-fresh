# Nexus owner preparation — source-only integration

The owner form selects saved build plans by readable titles, accepted contribution advice and source dependencies. Preparation retains an exact operation before any send. Reload performs no request; explicit recovery reads the existing result. An absent result leaves the same body and operation available for an explicit retry. Lost replies, bad acknowledgement hashes, revoked reads, unavailable source readers and browser storage failure preserve recovery truth.

`NexusOwnerService` composes the existing contribution aggregate and off-by-default `NexusProposalStore`. Its `referenceReader` is host configuration, never a field from an owner request. The private ModuleCore exposes `nexus_proposal_material()` and `verify_nexus_proposal(record)` as in-process host methods only. The source reader checks original Git blobs and retained pinned reviews, current owner/task/permission disclosure, immutable registry identity, and a final task/registry read. Review IDs are separately verified as owned accepted advice in the existing store. Advice is not an independent execution grant or proof of behavioral correctness.

Plans keep their original checkpoint and source review. An advisory proposal uses the current checkpoint and permission basis; it does not rewrite or reauthorize a historical plan. Changed permission scope still denies disclosure. Source references `mastermind/build-plan/<sha256>` and `mastermind/source-evidence/<sha256>` identify exact saved plans and their pinned input inventories. They are not archive addresses and do not claim to be original GPT/Claude excerpts. The current form includes at most 12 distinct source inventories in one proposal. Execution readiness remains a separate assessment, including cycles and historical-plan holds.

The form is intentionally not mounted, and no HTTP route or new hosted worker capability is installed. Required next integration: authenticated owner/worker envelope on the existing ledger, exact capability/policy and source pins, all-reader compatibility for migration038, then coupled rollout and real owner reload acceptance. An endpoint must derive the owner server-side, validate origin and bound payloads, and inject its pinned reader; it must never accept a client-supplied verification result. Delayed/uncertain verification cannot authorize a changed proposal. Actual creation still runs the SQL task/permission/series locks.

The new source remains local/private until exact public publication is approved. No production DB migration, worker dispatch, coding, model request, candidate execution, activation or deployment is part of these tests. Rollback for this source slice is to leave it uninstalled; after migration038 has history, compatible readers must be preserved.

Verification includes real private ModuleCore/PinnedBuildReviewProvider fixtures, cross-language Python→JS source proof with Unicode hashing, owner form interaction and no-send reload recovery. The cross-language service fixture uses a synthetic SQL adapter; prior PostgreSQL038 race acceptance remains separate and unchanged.
